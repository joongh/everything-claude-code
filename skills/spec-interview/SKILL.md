# 스펙 설계 인터뷰: 숨은 결정을 드러내기

자연어 요구사항("주문이 완료되면 알림 메일을 보낸다")은 기능 의도로는 자연스럽지만,
코드 수준에서는 그 안에 여러 기술 결정이 숨어 있다. 이 결정을 AI의 해석에 떠넘기지 않고,
**구현 전에 코드베이스를 근거로 드러내고 사람과 함께 확정**하기 위한 스킬이다.

핵심 원칙: **요구사항의 분량이 아니라, 어떤 결정이 필요한지 드러나는 구조가 중요하다.**

## 활성화 시점

- 새 기능 구현 요청 ("~ 기능 추가해줘", "~ 만들어줘")
- 기존 동작을 바꾸는 변경 작업
- 자연어 요구사항을 받았지만 트랜잭션 경계·실패 처리·호환성 등이 명시되지 않은 경우

단순 조회/질문, 한 줄짜리 기계적 수정, 이미 결정이 다 정해진 작업에는 쓰지 않는다.

## 워크플로우

### 1단계 — 코드베이스를 먼저 읽는다

구현을 시작하기 전에 관련 코드와 기존 컨벤션을 읽는다. 같은 "알림을 보낸다" 요구사항이라도
프로젝트마다 적절한 구현이 다르다. 이미 outbox 패턴이 있는지, 동기 외부 호출이 컨벤션인지,
이벤트 발행이 표준인지, 작업 큐/배치 재시도를 쓰는지 확인한다.

> 코드베이스를 읽지 않은 채로 추상적인 질문을 던지지 않는다.

### 2단계 — 이번 작업의 결정 축을 골라낸다

아래 결정 축 중 **이번 작업에서 실제로 갈리는 것만** 선택한다. 모든 축을 매번 묻지 않는다.

| 결정 축 | 확정해야 하는 질문 (예시) |
|---------|--------------------------|
| **Atomicity** | 두 작업을 같은 트랜잭션으로 묶어야 하는가? |
| **Idempotency** | 같은 이벤트가 두 번 처리되어도 결과는 한 번만 반영되어야 하는가? |
| **Failure-mode** | 한쪽 실패가 다른 쪽 상태(완료/롤백)에 영향을 주어야 하는가? |
| **Observability** | 요청·실패는 어떤 로그/이벤트/메트릭으로 추적되어야 하는가? |
| **Side-effects** | 외부 시스템 호출은 언제, 동기/비동기 어느 방식으로 발생하는가? |
| **Compatibility** | 기존 API·이벤트 계약이 바뀌지 않는가? |
| **Security** | 권한, tenant isolation, 입력 검증이 필요한가? |

작업 성격에 따라 핵심 축이 달라진다. 어떤 변경은 Atomicity/Failure-mode가, 어떤 변경은
Compatibility/Security가 핵심이다. 선택한 축과, **생략한 축의 이유**를 먼저 사용자에게 알린다.

예:
> 이번 작업은 알림 발송 기능 추가로 보입니다.
> 핵심 결정은 Atomicity / Idempotency / Failure-mode입니다.
> Observability는 실패 추적을 위해 짧게 확인하고, Compatibility는 기존 API 계약 변경이 없으므로 생략하겠습니다.

### 3단계 — grill-me 방식으로 하나씩 인터뷰한다

선택한 결정 축을 다음 네 가지 규칙으로 진행한다. (공개 스킬 `grill-me`의 인터뷰 골격을 빌림)

1. **한 번에 하나의 질문만 한다.**
2. **질문에는 추천 답을 함께 제시한다.** (사용자에게 판단을 떠넘기지 않는다)
3. **추상적인 원칙보다 관련 코드를 먼저 보여준다.**
4. **결정이 갈리는 순서대로 묻는다.**

나쁜 질문 — 너무 넓어 사용자가 맥락을 다시 떠올려야 한다:

> 알림 실패 시 어떻게 처리할까요?

좋은 질문 — 코드와 함께, 추천안을 곁들여 좁혀서 묻는다:

```kotlin
// option A — 트랜잭션 안에서 바로 알림 전송
@Transactional
fun completeOrder(orderId: OrderId) {
    val order = orderRepo.get(orderId)
    order.markCompleted()
    notificationClient.send(order)
}

// option B — commit 후 발행할 outbox만 저장
@Transactional
fun completeOrder(orderId: OrderId) {
    val order = orderRepo.get(orderId)
    order.markCompleted()
    outboxRepo.save(NotificationRequested(order.id))
}
```

> 이 코드베이스에는 이미 outbox 테이블과 발행 worker가 있습니다.
> 알림 실패가 주문 완료를 rollback시키면 안 된다면, B처럼 commit 이후 발행하는 방식이 더 적합합니다.
> 이 방향으로 확정할까요?

> **확인 요청은 [[user-confirmation]] 규칙에 따라 `AskUserQuestion`으로 한다.** 텍스트로 "어떻게 할까요?"라고 묻지 않는다.

목적은 AI가 모든 판단을 떠넘기는 것이 아니라 그 반대다. **AI가 코드베이스를 먼저 읽고
선택지를 좁혀 추천안을 제시하고, 사용자는 중요한 결정만 확정한다.**

### 4단계 — 확정된 결정만 스펙에 반영한다

인터뷰로 확정된 결정을 스펙(또는 구현 계획)에 명시적으로 적는다. 확정되지 않은 채로
"AI가 알아서" 결정하게 두지 않는다. 그 다음에 구현으로 넘어간다.

### 5단계 — 리뷰는 "결정이 반영됐는지" 확인하는 일이 된다

스펙 단계에서 결정이 드러나 있으면 리뷰 질문이 바뀐다. 코드를 처음부터 재해석하는 대신,
**합의된 결정이 코드에 반영됐는지** 확인한다.

- 스펙에서 확정한 트랜잭션 경계가 코드에 반영됐는가?
- 중복 방지 키가 합의한 기준대로 사용됐는가?
- 실패한 알림은 주문 완료 상태를 흔들지 않고 재시도 가능하게 남는가?
- 로그·이벤트는 합의한 관측 지점을 제공하는가?

## 안티패턴

- 자연어 요구사항을 그대로 구현 프롬프트로 넘기는 것 → 숨은 결정이 통제 밖으로 넘어간다
- 스펙을 길게 쓰는 것으로 해결하려는 것 → 분량이 아니라 결정 구조가 핵심이다
- 코드베이스를 안 읽고 일반론으로 질문하는 것 → 추천안 없는 넓은 질문은 인지 부하만 키운다
- 결정을 여러 개 한꺼번에 묻는 것 → 한 번에 하나씩
