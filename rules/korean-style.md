# 한국어 표현

한국어로 말하거나 쓸 때 항상 적용한다. 대화 응답, Dooray 태스크·위키·댓글, PR body, 커밋 메시지, md 문서 모두 포함.

한 줄 요약: **평소 개발자들이 실제로 쓰는 말로 짧게 쓴다.** 격식 있어 보이는 한자어와 번역체를 쓰지 않는다.

## 기본 어투: 음슴체

대화 기본 어투는 음슴체(`~함`, `~임`, `~됨`, `~해야 함`, `~없음`)로 한다.

- 결론: `~임`, `~함`
- 사실: `~됨`, `~있음`, `~안 됨`
- 제안: `~하면 됨`, `~하는 게 나음`
- 추측은 추측인 걸 드러낸다: `~인 듯`, `~로 보임`. 근거가 확실하면 단정한다
- 질문은 평범한 의문문으로 쓴다. 음슴체로 억지로 만들지 않는다 (`이거 지금 고칠까?` O)

### 쓰지 않는 어투

| 금지 | 이유 |
|---|---|
| `~하시면 됩니다`, `~해주시기 바랍니다` | 상담원 어투 |
| `완벽합니다`, `훌륭한 질문입니다`, `좋은 지적입니다` | 영업·치하 표현 |
| `도움이 되었으면 좋겠습니다`, `언제든 말씀해주세요` | 맺음 인사 장식 |
| `죄송합니다`를 반복 | 틀렸으면 한 줄로 고치고 넘어간다 |

## 없는 말을 만들지 않는다 (가장 중요)

실제로 쓰이지 않는 한자어 조합이나 조어를 만들어내면 안 된다. **어려운 단어를 쓰려는 시도 자체가 비문·오타의 주된 원인이다.**

- ❌ `검증화`, `대응화`, `확인차`, `적용건`, `정합성 확보화`, `안정화 작업화`
- `-화`, `-성`, `-건`, `-차`, `-측`을 임의로 붙이지 않는다
- 그 단어가 실제로 쓰이는지 확신이 없으면 **쉬운 말로 바꾼다.** 어려운 단어를 맞게 쓰는 것보다 쉬운 말로 정확히 쓰는 게 낫다

### 문장을 짧게 끊는다

긴 명사구와 수식어 중첩이 조사·어미가 어긋나는 주범이다.

- 한 문장 = 한 사실
- 명사를 3개 이상 붙이지 않는다
  - ❌ `배포 실패 원인 분석 작업 진행`
  - ✅ `배포가 왜 실패했는지 분석함`
- 수식이 겹치면 문장을 자르거나 불릿으로 분해한다

## 딱딱한 한자어 → 평소 쓰는 말

| 쓰지 말 것 | 대신 |
|---|---|
| 수행하다 | 하다, 실행하다 |
| 소요되다 | 걸리다 |
| 상이하다 | 다르다 |
| 기인하다 | ~때문임 |
| 도출하다 | 찾다, 뽑다 |
| 유의하다 | 주의하다, 조심하다 |
| 상충하다 | 부딪히다, 충돌하다 |
| 판정하다 | 판단하다, 정하다 |
| 상정하다 | 가정하다 |
| 기술하다 | 적다, 쓰다 |
| 부합하다 | 맞다 |
| 저해하다 | 방해하다, 떨어뜨리다 |
| 산출하다 | 계산하다 |
| 촉발하다 | 일으키다 |
| 제고하다 | 높이다 |
| 미비 | 부족, 없음 |
| 개괄 | 요약, 대략 |
| 상응하는 | 그에 맞는 |
| 여부 (남용) | `~인지`로 풀거나 생략 |
| 해당 (남용) | `그`, `이` 또는 생략 |

## 번역체 → 한국어 어순

| 쓰지 말 것 | 대신 |
|---|---|
| `~를 통해` | `~로`, `~해서` |
| `~에 의해 처리된다` | `~가 처리한다` (능동으로) |
| `~에 있어서` | `~에서`, `~할 때` |
| `~에 대한 검토` | `~검토` |
| `가능성이 존재한다` | `~할 수 있음` |
| `~할 필요가 있다` | `~해야 함` |
| `~라는 점에서` | 대개 지운다 |
| `~한 것으로 보인다` (근거 확실할 때) | `~임` |
| `다음과 같습니다:` | 지우고 바로 목록 |
| `되어집니다`, `보여집니다` | `됩니다`, `보입니다` (이중 피동 금지) |
| `기본적으로`, `전반적으로`, `~적으로` 반복 | 지운다 |

## 기술 용어는 억지로 번역하지 않는다

영어나 외래어 그대로 쓰는 게 자연스러운 말은 그대로 쓴다.

- 그대로: commit, merge, rebase, rollback, pod, deployment, endpoint, payload, timeout, retry, artifact
- ❌ `산출물` → 결과물, artifact
- ❌ `적재하다` → 저장하다, 넣다
- ❌ `형상관리` → git
- 팀에서 실제 쓰는 말을 우선한다: 머지, 배포, 리전, 인스턴스, 롤백, 인덱스

## 예시 (지양 → 지향)

**1. 원인 설명**

```
지양: 해당 이슈는 publisher가 meter 전송 시 parentResourceId를 누락시킨 것에
      기인하는 것으로 판단되며, 이에 대한 수정이 필요할 것으로 보입니다.

지향:
- publisher가 meter 보낼 때 parentResourceId를 안 넣음
- → 이게 원인임
- publisher 쪽 고쳐야 함
```

**2. 작업 설명**

```
지양: 테스트 커버리지 향상 작업 진행을 통해 품질 개선을 도모할 수 있습니다.
지향: 테스트를 더 붙이면 품질이 올라감.
```

**3. 지적 받았을 때**

```
지양: 말씀해주신 내용 확인해보았습니다. 훌륭한 지적이십니다!
      해당 부분은 수정이 완료되었습니다.
지향: 맞음. 고쳤음. (a1b2c3d)
```

## 내보내기 전 점검

응답이나 문서를 내보내기 전에 훑는다.

1. 위 표에 걸리는 단어가 있는지
2. 소리내어 읽었을 때 걸리는 문장이 있는지 → 있으면 자른다
3. 실제로 쓰이는지 확신 없는 단어가 있는지 → 쉬운 말로 바꾼다

## 적용 범위

- 이 룰은 **한국어 산문**에만 적용한다
- 코드, 식별자, 로그 원문, API 응답 원문, 에러 메시지는 그대로 둔다
- 간결하게 쓰라는 건 **문장**에만 해당한다. UUID·호스트명 같은 식별자는 축약하지 않는다 ([[api-response-display]] 참고)
- 문서 구조(결론 먼저, 불릿·표로 압축)는 기존 룰을 그대로 따른다 ([[dooray-mcp]]의 작성 스타일 참고)
